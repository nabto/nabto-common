# Coap client and server

A CoAP (RFC 7252) client and server written in C for the Nabto
platform. The library is transport agnostic: it has no sockets and no
DTLS. The integrator hands incoming packets to the library together
with an opaque `connection` pointer and pulls outgoing packets out of
it. Security and multiplexing are the job of the surrounding Nabto
connection.

## Structure

| File | Contents |
|---|---|
| `src/nabto_coap.c` | Shared message parser and encoder, option iterator, stamp arithmetic |
| `src/nabto_coap_client_impl.c` | Client: requests, retransmission, block-wise reassembly, observe |
| `src/nabto_coap_server_impl.c` | Server: route tree, responses, retransmission, observers |
| `src/nabto_coap_server_impl_incoming.c` | Server: incoming packet handling, block-wise reassembly |
| `src/nabto_coap_client_test.c` | Helpers for unit tests only, not part of the protocol |

Both client and server are driven by the integrator's event loop:
`nabto_coap_client_get_next_event` / `nabto_coap_server_next_event`
say whether there is a packet to send, a timeout to wait for
(`*_get_next_timeout`) or nothing to do, and the `notifyEvent`
callback asks the integrator to run the loop again. Memory comes from
an `nn_allocator`. There are no static limits, but reassembly can be
bounded with `nabto_coap_server_limit_requests`,
`nabto_coap_server_limit_request_size` and
`nabto_coap_client_limit_response_size`.

## RFC 7252, CoAP core

### Implemented

| Area | Status |
|---|---|
| Message format | Header, 0-8 byte token, option delta/length with 1 and 2 byte extensions (reserved nibble 15 rejected), payload marker, version check. `nabto_coap_parse_message` validates the whole option list before a message is acted on. |
| Message types | CON, NON, ACK and RST on both sides. The client sends CON by default, `nabto_coap_client_request_set_nonconfirmable` selects NON. The server answers with the type of the request. |
| Reliability | Exponential back-off with `ACK_TIMEOUT` 2 s and `MAX_RETRANSMIT` 4; the client can change both in `settings`, the server uses the constants. Timeouts are clamped to the 32 bit stamp range. The server retransmits CON responses and CON notifications, NON responses are never retransmitted. |
| Deduplication | Server: a retransmitted request (same token and message id on a connection) is ACKed again, or the 2.31 Continue is resent, but the request is processed once. A retransmitted NON is ignored. |
| Piggybacked vs separate responses | Server: errors generated by the library (4.00, 4.02, 4.04, 4.08, 4.13, 5.03) and the Block1 2.31 Continue are piggybacked in the ACK. Every application response is separate: an empty ACK followed by a CON or NON response with its own message id. The client handles both forms. |
| Matching | Request to response by token and connection; ACK and RST by message id and connection, and only against a response or notification that has been sent and not yet acknowledged. |
| Methods and codes | GET, POST, PUT and DELETE. All response codes of section 12.1.2 are defined, `nabto_coap_server_response_set_code_human(404)` converts from the dotted form. |
| Options | Uri-Path (server routing with `{parameter}` segments), Content-Format, Block1, Block2 and Observe. Uri-Host and Uri-Port are accepted and ignored. Any other critical option is answered with 4.02 Bad Option for a CON request and a RST for a NON request (section 5.4.1). Unknown elective options are ignored. |
| Error responses | Carry a diagnostic payload without Content-Format (section 5.5.2). The server holds one pending error, one empty ACK and one RST; further ones are dropped and recovered by the peer's retransmission. |
| RST | The client resets a CON or NON it has no request for and a response arriving after the request has been cancelled. A RST for a response in flight ends the request, a RST for a notification removes the observer. |

### Not implemented

- Proxying: Proxy-Uri and Proxy-Scheme are rejected with 4.02.
- Caching and validation: Max-Age, ETag, If-Match, If-None-Match and
  2.03 Valid. If-Match and If-None-Match are critical and rejected
  with 4.02.
- Accept and Uri-Query are critical and rejected with 4.02. There is
  no API for Location-Path, Location-Query or Size1.
- Resource discovery (`/.well-known/core`, RFC 6690), multicast and
  `coap://` URI handling.
- Message size limits; the size of the integrator's buffer decides.
- `ACK_RANDOM_FACTOR`, `NSTART`, `PROBING_RATE` and `EXCHANGE_LIFETIME`
  bookkeeping. Message ids and tokens are sequential counters
  starting from zero.
- CoAP ping (an empty CON): the client answers with a RST as
  required, the server answers with 4.04 Not Found.
- Piggybacked application responses on the server, see the design
  notes below for the reasoning.

## RFC 7959, block-wise transfers

### Client

- Block1 for request bodies, fixed 512 byte blocks (SZX 5).
- Block2 reassembly of response bodies at the block size chosen by
  the server, with checks of the offset and of the length of each
  block. `nabto_coap_client_limit_response_size` bounds the
  reassembled body.
- Missing: early negotiation of the response block size, Size1 and
  Size2, using a 4.13 as a hint to switch to smaller blocks.

### Server

- Block1 reassembly with 2.31 Continue for each chunk; 4.08 Request
  Entity Incomplete on a gap, 4.00 Bad Request on a chunk of the
  wrong length or the reserved SZX 7, 4.13 Request Entity Too Large
  above `nabto_coap_server_limit_request_size`. The Block1 option is
  echoed in the first response.
- Block2 serving with 512 byte blocks by default and late negotiation
  (the client can ask for smaller blocks). A block past the end of the
  body is a 4.00. The response is kept until the last block has been
  ACKed.
- Missing: Size1 and Size2.

## RFC 7641, observe

### Client

- `nabto_coap_client_request_observe` registers (Observe=0),
  `nabto_coap_client_request_observe_deregister` deregisters
  (Observe=1). Every notification is delivered through the end handler
  with status `NABTO_COAP_CLIENT_STATUS_OBSERVE_NOTIFICATION` and the
  sequence number is available from
  `nabto_coap_client_response_get_observe`. CON notifications are
  ACKed and there is no idle timeout while observing.
- Missing: the reordering check of section 3.4 (every notification is
  accepted in the order it arrives) and re-registration based on
  Max-Age.

### Server

- `nabto_coap_server_request_is_observe`,
  `nabto_coap_server_request_accept_observe`,
  `nabto_coap_server_resource_notify` and
  `nabto_coap_server_remove_observer`. Notifications are CON with
  retransmission; an update arriving while one is in flight is kept
  in a single pending slot and sent when the in-flight one is ACKed.
  An observer is removed on a RST, when retransmissions are exhausted,
  on deregistration and when its connection is removed.
- Missing: NON notifications (no API to select them), Max-Age and ETag
  on notifications, cancelling an observation from the server with an
  error response.

## Design notes

### How long can it be from a request is made until a response is ready

A CoAP exchange has a limited timespan, but a CoAP request/response
can take as long as the connection is alive. The client therefore
only bounds the wait for a response with the timeout the caller sets
on the request (`nabto_coap_client_request_set_timeout`, two minutes
by default).

### Why there are no tokens in ACK and RST messages

RFC 7252 section 4.4 states that ACK and RST are correlated with the
message they answer by message id alone, and elsewhere that an empty
ACK is a four byte message. Each CON transmission is identified by
its message id and endpoint, so a token is not needed.

### Piggybacked vs separate responses

With piggybacked responses, i.e. sending the response in the ACK, the
server has to keep the response state until it is sure that the client
will not retransmit the request. With separate responses the client
must ACK the response, so the server only keeps the response state
until that ACK arrives. The server therefore always sends application
responses as separate responses.

### Route tree

The resources of a server form a route tree of path segments; a
segment written as `{name}` is a parameter whose value is available to
the handler through `nabto_coap_server_request_get_parameter`. Each
node holds one handler per method:

```
/iam/users                        GET, POST
/iam/users/{user}                 GET, DELETE
/iam/users/{user}/roles/{role}    PUT, DELETE
/iam/roles                        GET, POST
/iam/roles/{role}                 GET, DELETE
/iam/roles/{role}/policies/{policy}  PUT, DELETE
```

The tree is built by `nabto_coap_server_add_resource` from a NULL
terminated segment array, e.g. `{ "iam", "users", "{user}", NULL }`,
and is represented by `struct nabto_coap_router_node` in
`src/nabto_coap_server_impl.h`.

## Not implemented at all

RFC 8323 (CoAP over TCP, TLS and WebSockets), RFC 8132 (FETCH, PATCH
and iPATCH), RFC 7967 (No-Response), RFC 8613 (OSCORE), RFC 8974
(extended tokens) and RFC 6690 (link format).

# Tests

Unit tests for the server live in `test/` and are built by the
Boost.Test project in `ci-build/`. Boost is provided by the vcpkg
submodule in `3rdparty/vcpkg` (manifest in `ci-build/vcpkg.json`):

```
./3rdparty/vcpkg/bootstrap-vcpkg.sh -disableMetrics
cmake -B build -S components/coap/ci-build \
  -DCMAKE_TOOLCHAIN_FILE=$PWD/3rdparty/vcpkg/scripts/buildsystems/vcpkg.cmake
cmake --build build --parallel
./build/coap_test
```

The library and the tests are built with AddressSanitizer and
UndefinedBehaviorSanitizer; pass `-DNABTO_COAP_SANITIZE=OFF` to cmake
to disable that. The same steps run in `.github/workflows/coap_ci.yml`.
Further tests are located in the private nabto-common-cpp repository.
